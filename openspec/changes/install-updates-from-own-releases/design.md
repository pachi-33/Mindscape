# Design

## Context

当前 `UpdateChecker` 管理首启询问、手动检查、后台提醒和下载，`GitHubUpdateService` 默认读取上游仓库。现有「保存并退出」只打开安装包，`MapEditor.saveNow()` 又不会把写入失败传给调用方。新版需要在同一更新会话中等候验签和保存结果，再让安装器接管退出与重启。

## Goals / Non-Goals

**Goals**

- 发布入口、更新目录和人工下载入口指向 `pachi-33/Mindscape`。
- 一个用户操作启动整个安装流程，并在退出前确认导图安全落盘。
- 失败时可以留在旧版修复问题或重试，并且可用两个签名版本复验流程。

**Non-Goals**

- 静默安装、自定义替换脚本、增量包，以及由 PR 合并自动触发公开发布。

## Decisions

1. **使用 Sparkle 2 安装与重启。** 通过 XcodeGen 接入固定版本的 Swift Package，由应用级更新协调器持有单一 Sparkle 更新会话，复用现有菜单和设置入口。使用 Sparkle 的安装与重启能力，避免自行管理提权、应用替换和进程重启。对照 [程序化接入说明](https://sparkle-project.org/documentation/programmatic-setup/)。
2. **用稳定的目录地址引用版本化附件。** 将 Sparkle 更新目录（appcast）放在自有仓库 `main` 上的固定 HTTPS 路径，目录中的 ZIP 指向自有仓库对应 tag 的 GitHub Release。发布脚本显式指定仓库与已验证提交，先确认已发布的附件可获取，再更新目录。首个过渡版发布后应有可读的目录。通过目录中的预发布通道和兼容元数据过滤候选，按递增的 `CFBundleVersion` 排序，保留面向用户的语义版本号。稳定版只接收正式通道，预发布版还接收预发布通道。固定地址允许两类发布按各自节奏迭代，且不会因为稳定版的 `releases/latest` 跳过预发布条目。
3. **提前验证签名并绑定应用身份。** 正式应用使用 Developer ID 签名和 Apple 公证，更新归档使用 Sparkle EdDSA 签名，正式客户端嵌入公钥。启用解包前验证并签名更新目录。私钥留在签名环境中，发布流程遇到缺失的签名材料或无效的签名、应用标识、版本信息时中止。人工分发可保留 DMG 和 SHA-256，应用内更新以签名为准。对照 [发布说明](https://sparkle-project.org/documentation/publishing/)与[安全设置](https://sparkle-project.org/documentation/customization/#security-settings)。
4. **在安装许可交给 Sparkle 前完成保存。** 用户点击「更新」后显示进度。用 Sparkle 用户交互回调承接已授权的安装会话，在安装与重启前提交当前就地编辑并调用能返回失败的同步保存入口。若仅使用内存库且有未落盘的数据，或编辑与写入失败，保留编辑器并取消本次安装。取得保存成功后才允许安装与退出，在交接期间阻止新编辑。若用户在安装准备期间直接退出，也按相同保存条件处理，防止在未保存时触发退出安装。取消准备好的安装时使用明确取消语义，避免把更新留到下次退出时安装。对照 [Sparkle 用户交互回调](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUserDriver.html)。
5. **保持检查偏好，切断旧更新状态。** 新版只由一个调度器驱动。首启询问、启动检查、运行期间 24 小时节流及手动检查反馈按现有规格保留。迁移时沿用是否自动检查及是否已询问的偏好，不使用上游发布缓存、ETag、跳过版本或检查时间。未点击「更新」时只提示可用版本。

## Risks / Trade-offs

- 应用位于只读卷或系统授权被取消时可能无法替换。显示失败原因及自有仓库的人工安装入口。验签失败则阻止安装该文件。
- 本地测试用公钥和目录与正式环境隔离。单元测试覆盖迁移、失败分支和版本过滤，真实替换与重启用独立文稿库及两份签名应用验收。
- 发布不能依赖只有最新条目的目录。保持可用的稳定版条目和相应的不可变附件地址，发布失败时不提前替换目录。

## Migration Plan

1. 手动安装首个包含新更新器的版本，沿用现有 bundle ID 和数据目录。集成前的客户端仍查询原上游仓库。
2. 在隔离环境用后续版本验证点击更新、重启与重新打开文稿库，再验证故意制造的写入和验签失败。
3. 经发布授权后上传正式附件并更新签名目录。如果需停止有问题的版本，从更新目录撤下该候选，保留可安装的已知良好版本。已经安装问题版本的用户通过更高构建号的修复版恢复。
